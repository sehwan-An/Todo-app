# TRD - Todo App (초안)

> 원본: docs/PRD.md, docs/CLAUDE.md
> 상태: 초안. "미정" 표시 항목은 결정 후 갱신한다.

## 1. 기술 스택과 선택 이유

| 기술 | 역할 | 고른 이유 (한 줄) |
|---|---|---|
| Next.js 15 (App Router) | 웹 앱 프레임워크 | 화면과 API 서버를 한 프로젝트에서 만들 수 있어, 프로젝트를 둘로 나눌 필요가 없다. |
| React 19 | 화면 구성 | 화면을 버튼, 목록 같은 작은 조각(컴포넌트)으로 나눠 만들 수 있다. |
| TypeScript (strict) | 언어 | 값의 종류(타입)를 미리 정해 두면, 실행 전에 오타와 실수를 잡아준다. |
| Tailwind CSS | 스타일 | CSS 파일을 따로 만들지 않고 class 이름만으로 모양을 꾸밀 수 있다. |
| MySQL 8 | 데이터베이스 | 가장 널리 쓰이는 DB 중 하나라 자료가 많고, 무료로 쓸 수 있는 호스팅도 많다. |
| Drizzle ORM | DB 연결 도구 | SQL을 TypeScript 코드처럼 쓸 수 있고, 테이블 구조가 타입으로 자동 연결된다. |
| Zod | 입력 검증 | "제목 1~100자" 같은 규칙을 한 곳에 정의해 화면과 서버에서 똑같이 쓸 수 있다. |
| Jest | 테스트 실행 | 가장 많이 쓰이는 JavaScript 테스트 도구라 자료와 예제가 많다. |
| React Testing Library | 화면 테스트 | 사용자가 실제로 클릭하고 입력하는 방식 그대로 화면을 테스트한다. |

## 2. 구조 개요

```
[브라우저]                         [Next.js 서버]                  [DB 서버]
화면 컴포넌트  --HTTP 요청(JSON)-->  API 라우트 --> 서버 로직 --> Drizzle --> MySQL
(src/components)                   (app/api)     (src/lib)
              <--HTTP 응답(JSON)--
```

| 폴더 | 담는 것 |
|---|---|
| app/ | 페이지(화면 진입점)와 API 라우트 |
| src/components/ | 화면 컴포넌트 (입력창, 목록, 항목) |
| src/lib/ | 서버 로직, DB 연결, Zod 검증 규칙 |
| src/types/ | 화면과 서버가 함께 쓰는 타입 (예: 할 일의 모양) |

## 3. 버전별 데이터 저장 위치

| 버전 | 저장 위치 | 새로고침 | 서버 재시작 |
|---|---|---|---|
| v0.1 | 브라우저 메모리 (React 상태) | 사라짐 | - |
| v0.2 | 서버 메모리 (서버의 배열 변수) | 유지 | 사라짐 |
| v0.3 | MySQL | 유지 | 유지 |
| v1.0 | MySQL + 배포 | 유지 | 유지 |

- v0.1 → v0.2: 화면은 그대로 두고, 데이터를 서버에 요청하도록 바꾼다.
- v0.2 → v0.3: API는 그대로 두고, 서버 로직(src/lib) 안의 저장 방식만 DB로 바꾼다.
- 즉, 한 버전에서 한 층만 바뀌도록 설계한다.

## 4. 흐름: "추가" 버튼을 누른 뒤 DB에 저장되기까지 (v0.3 기준)

1. **입력**: 사용자가 입력창에 제목을 쓰고 "추가" 버튼을 누른다.
2. **화면에서 검증**: 화면 컴포넌트가 Zod 규칙으로 제목을 검사한다.
   - 앞뒤 공백을 지운 뒤, 0자(빈 제목, 공백만)이거나 100자를 넘으면 여기서 멈추고 에러 메시지를 보여준다. (서버에 요청하지 않음)
3. **요청 보내기**: 검증을 통과하면 브라우저가 서버에 "할 일 추가" 요청을 보낸다.
   - 예: `POST /api/todos`, 내용 `{ "title": "우유 사기" }` (자세한 내용은 API_SPEC.md)
4. **API 라우트가 받기**: app/api 안의 API 라우트가 요청을 받는다.
5. **서버에서 다시 검증**: 같은 Zod 규칙으로 한 번 더 검사한다.
   - 화면 검증은 우회할 수 있으므로 서버 검증이 진짜 안전장치다.
   - 실패하면 400 에러 응답을 돌려준다.
6. **서버 로직 호출**: API 라우트가 src/lib의 "할 일 만들기" 함수를 부른다.
7. **DB에 저장**: 서버 로직이 Drizzle로 todos 테이블에 새 행을 넣는다. 제목은 앞뒤 공백을 지운 값으로 저장한다.
   - DB가 id와 만든 시간을 채우고, 완료 여부는 기본값 "미완료"로 저장된다.
8. **결과 돌려받기**: DB가 저장된 행을 돌려주고, API 라우트는 이를 JSON으로 응답한다. (201)
9. **화면 갱신**: 화면이 응답받은 할 일을 목록 맨 위에 추가한다. (최신순)
10. **실패 처리**: 서버나 DB 오류가 나면 목록은 그대로 두고 에러 메시지를 보여준다. (문구 미정)

- 완료 전환(F-03), 삭제(F-04)도 같은 흐름을 따른다. 요청 종류와 DB 동작만 다르다.
- v0.2에서는 7단계가 "서버의 배열에 넣기"로 바뀌고, 나머지는 같다.

## 5. 데이터 (개략)

할 일 하나가 가지는 값. 정확한 정의는 docs/DATA_MODEL.md에서 확정한다.

| 값 | 설명 |
|---|---|
| id | 할 일을 구분하는 고유 번호 |
| title | 제목 (1~100자) |
| completed | 완료 여부 (기본값: 미완료) |
| createdAt | 만든 시간 (최신순 정렬 기준) |

## 6. 비기능 요구사항
- **타입 안정성**: TypeScript strict 모드, any 타입 금지
- **검증 일원화**: 제목 규칙(PRD "제목 규칙")은 Zod 스키마 하나로 정의하고 화면과 서버가 함께 쓴다.
  - Zod의 기본 길이 검사는 JavaScript `length` 기준이라 "👍"를 2자로 센다.
  - 그래서 글자 수는 코드 포인트 단위로 직접 세도록 규칙을 만든다. (MySQL `CHAR_LENGTH`와 같은 기준)
- **비밀값 관리**: DB 접속 주소는 환경 변수로 관리하고 저장소(git)에 올리지 않는다.
- **테스트**: Jest + React Testing Library. 테스트 케이스는 docs/TEST_CASES.md를 따른다.

## 7. 미정 사항
- 배포처 (Next.js 앱)
- MySQL을 어디서 운영할지 (개발: 내 PC에 설치 / 배포: 클라우드 MySQL 서비스)
- 화면에 보여줄 에러 문구 (API의 message를 그대로 쓸지)
